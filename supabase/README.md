# Supabase для AthleteMenu

Схема рассчитана на прямые запросы из браузера. Доступ к строкам ограничивают политики PostgreSQL RLS; ключ `service_role` в браузерный код помещать нельзя.

## Установка

1. Создайте проект в Supabase и откройте **SQL Editor → New query**.
2. Выполните `setup.sql` целиком, чтобы создать таблицы, функции и RLS-политики и загрузить начальные справочники. Объединённый скрипт можно выполнять повторно. При необходимости он разделён на `schema.sql` и `seed.sql`.
3. Укажите Project URL и публичный anon/publishable key в `assets/js/config.js` из **Project Settings → API**. Файл можно создать копированием `assets/js/config.example.js`. Не вставляйте `service_role` / secret key.
4. В **Authentication → URL Configuration** задайте адрес локального сайта и разрешённые redirect URL.
5. Через форму регистрации приложения создайте аккаунт будущего администратора. Новая учётная запись сначала получает роль спортсмена.
6. Для первого администратора один раз назначьте роль в SQL Editor, подставив его email:

   ```sql
   update public.profiles p
   set role = 'admin'
   from auth.users u
   where p.id = u.id and lower(u.email) = lower('admin@example.com');
   ```

   Это начальная настройка выполняется в привилегированном SQL-контексте; обычный пользователь не может назначить себе роль.

7. Выполните `roles.sql` в SQL Editor. После этого администратор сможет открывать в AthleteMenu раздел **Пользователи** и назначать роли спортсмена, тренера или администратора по электронной почте. Функции доступны только роли admin; последний администратор и собственная роль текущего администратора защищены от случайного снятия.
8. В SQL Editor запустите `tests.sql` после замены тестовых UUID в файле на реальные ID аккаунтов и записей, как объяснено в начале файла.

## Таблицы и связи

- `auth.users` 1—1 `profiles`; профиль 1—1 `athlete_profiles`.
- `sports` 1—N `athlete_profiles`, `training_sessions`; `product_groups` 1—N `products`.
- `profiles` (тренер) N—M `profiles` (спортсмен) через `coach_athletes`. Связь получает доступ к данным только в статусе `active`, который устанавливает спортсмен при принятии заявки.
- `profiles` (владелец) 1—N `menus`; `menus` 1—N `menu_days` 1—N `meals` 1—N `menu_items`.
- `menu_items.product_id` необязателен. Название и значения ккал/БЖУ сохраняются снимком, поэтому последующие изменения `products` не меняют старые меню.
- `profiles` 1—N `training_sessions`, `nutrition_results`, `weight_log`.

`v_menu_day_totals` вычисляет сумму ккал и БЖУ из сохранённых снимков по формуле `масса в граммах × значение на 100 г / 100`.

## Доступ и роли

- `anon` не имеет SQL-прав на прикладные таблицы и представление. Все политики таблиц выданы только роли `authenticated`.
- `athlete`: читает и изменяет собственные профильные данные, меню, тренировки, результаты питания и вес; читает каталоги. Чужие строки не видит.
- `coach`: после подтверждения спортсменом читает/изменяет разрешённые данные закреплённого спортсмена. Заявка `pending` доступа не даёт. Запрос закрепления создаётся RPC `request_coach_athlete_link(email)` или прямой вставкой только со статусом `pending`.
- `admin`: читает профили и пользовательские данные, а также управляет справочниками. Изменять роль может только администратор или привилегированный SQL-контекст.
- Изображения профиля используют совместимый публичный bucket `athletemenu-avatars`: объекты доступны по публичному URL, запись/изменение/удаление — только владельцу папки `{auth.uid()}`. RLS на таблицы базы данных остаётся закрытым для `anon`.

## Примечание о совместимости

В схеме сохранены прежние названия некоторых полей, которые использует текущая версия AthleteMenu (например, `quantity_g`, `duration_minutes`, `period_start`). Триггеры синхронизируют их с каноническими колонками (`grams`, `duration_min`, `start_date`). Это позволяет подключать базу поэтапно без массового переписывания экранов. Если проект разворачивается с нуля, старые таблицы `coach_link_requests` и `weight_entries` создаются/сохраняются как совместимые.

## Пищевая ценность

Начальные значения в `seed.sql` — типовые ориентиры на 100 г, а не данные конкретной марки или рецепта. Для точных значений конкретных продуктов смотрите [USDA FoodData Central](https://fdc.nal.usda.gov/) и этикетку продукта. Состав базы USDA обновляется; числовые значения могут отличаться по сырью и способу приготовления.
